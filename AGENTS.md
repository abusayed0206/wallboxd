# AGENTS.md

Windows-only Rust system-tray app, product name **Wallboxd** (crate/package name `wallboxd`, binary `Wallboxd.exe`), that sets the desktop wallpaper (and, for the packaged MSIX build, the lock screen too) to a Letterboxd user's poster wall, generated **locally** - the app fetches the user's public Letterboxd diary RSS and poster images directly and composites the wall in-process with the `image` crate. The compositing/layout math is a Rust port of a TypeScript reference implementation (`posterLayout.ts`/`wallpaper.jpg.ts`/`letterboxd.ts`) at `F:\Github\lb` in this environment - keep `poster_layout.rs`/`wallgen.rs`/`letterboxd.rs` in sync with it if the layout math or Letterboxd's CDN rules change. User-facing docs live in `README.md`; this file is agent guidance. MSIX packaging/Store-identity docs live in `packaging/README.md`.

## Editing Win32 code

- Load the repo-local skill `.opencode/skills/rust-windows/SKILL.md` before touching any Win32 code (window procedures, tray, dialogs, registry, wallpaper). Key gotchas it covers:
  - `windows` crate **features are opt-in per API** - using a new API means adding its feature in `Cargo.toml`; a missing feature fails at compile time.
  - Runtime strings need null-terminated UTF-16 buffers (`s.encode_utf16().chain(std::iter::once(0))`); compile-time literals use `w!("...")`.
  - Two error styles coexist: newer bindings return `Result<_, Error>` (`?`/`.map_err`), older ones return a raw `WIN32_ERROR` converted with `.ok()` (sometimes `.ok().ok()`). See `open_run_key()` in `autostart.rs`.
- `Cargo.lock` is committed - CI and the release workflow build with `--locked`.

## Build / verify

- **Windows-only**: Win32 via the `windows` crate; CI runs on `windows-latest`. Won't build on other platforms.
- **Edition 2024** with let-chains (`if let Some(cfg) = cfg && !cfg.username.is_empty()` in `main.rs`, and elsewhere) - requires a recent stable Rust toolchain.
- CI gate order (all must pass): `cargo fmt --all -- --check` → `cargo clippy --all-targets --all-features --locked -- -D warnings` → `cargo build --release --locked` → `cargo test --release --locked`.
- Local iteration: `cargo bq` (the `quick` profile in `Cargo.toml`, alias in `.cargo/config.toml`) builds optimized without LTO/single-CGU, so incremental rebuilds take a few seconds. CI and the release workflow stay on `--release`.
- Tests (all fast and offline): `wallpaper::tests::concurrent_refresh_guard_rejects_overlap` (refresh race, see "Concurrency" below), `config::tests::parse_*` (UTF-8 BOM and legacy config loading), `uifont::tests::*` (DPI-scaled message font), `wallgen::tests::blank_detection_*` (blank-wall guard). `cargo fmt --all -- --check` and `cargo clippy --all-targets --all-features -- -D warnings` are both **fully clean** (zero issues) across the whole repo as of the most recent pass - keep it that way; don't let new code reintroduce warnings.
- `#![windows_subsystem = "windows"]` - no console. Diagnostics go to `%LOCALAPPDATA%\Wallboxd\Wallboxd.log` via `applog`; never `println!`.

## Release

- Pushing a tag `v*.*.*` triggers `release.yml`, which **fails if the tag version ≠ Cargo.toml `version`, or ≠ `packaging/AppxManifest.xml`'s `Version` minus its trailing `.0`**. Bump both before tagging.
- Publishes two assets per GitHub Release: `dist/Wallboxd-$version-windows-x64.zip` (plain exe, `target/release/Wallboxd.exe`) and `dist/Wallboxd-$version-windows-x64.msix` (built via `packaging/build-msix.ps1 -SkipBuild`, same script used for local sideload testing - see `packaging/README.md`). The MSIX in the release is **unsigned** (same as the one meant for Partner Center upload) - Windows won't install it without the local test-signing/sideloading steps in `packaging/README.md`; it's there for anyone who wants package identity (lock screen support) without waiting on the Store listing, not as a one-click installer. **The plain exe can't set the lock screen at all** (no package identity - see "Lock screen" below); only the MSIX build can.
- `[profile.release]` in `Cargo.toml` (`opt-level = 3`, `lto = true`, `codegen-units = 1`, `strip = true`) is tuned for Store submission: cut the binary from 6,560,256 to 5,841,408 bytes (~11%) on this build. **Deliberately not `panic = "abort"`**: `wallgen::fetch_all_posters`'s worker pool does `queue.lock().unwrap()` on a shared `Mutex`, and other `.unwrap()`s exist across background refresh threads - `panic = "abort"` would turn any single panic anywhere into the entire tray app silently vanishing (no tray icon, no log entry), which contradicts the "resilient by design" architecture (see "Gotchas" below). `panic = "unwind"` (the default, left unset) keeps a panicking thread's failure contained to that thread. Don't add `panic = "abort"` back without first removing or hardening every `.unwrap()`/`.expect()` that can run on a background thread.

## Runtime data

- Everything lives in `%LOCALAPPDATA%\Wallboxd` (via `config::data_dir()`): `config.json`, `wallpaper.jpg`/`lockscreen.jpg` (cache), `Wallboxd.log`, plus transient `lockscreen_{timestamp}.jpg` files (see "Lock screen"). `LOCALAPPDATA` is required - the code `.expect()`s it.

## Architecture

- `main.rs` - hidden, never-shown message-only window that owns the tray icon, refresh timer, and settings dialog. Single-instance via named mutex `Local\WallboxdSingleInstanceMutex` (second launch exits silently). Refresh runs on a spawned thread; current `Config` lives in a `thread_local!`.
- `build.rs` - embeds `assets/icon.ico` into the exe as Windows resource ID `"1"` via the `winresource` build-dependency (`res.set_icon_with_id("assets/icon.ico", "1")`). The lowest-numbered icon resource in a PE file is what Explorer/Task Manager/Alt-Tab show as the executable's own icon, so this one file covers that automatically. Confirmed via `[System.Drawing.Icon]::ExtractAssociatedIcon()` on the built exe that the correct icon is actually embedded and extractable (see "Icon" below for why that check matters more than it sounds).
- `appicon.rs` - `load() -> HICON` loads that same embedded resource (ID `1`) via `LoadIconW`, falling back to the stock `IDI_APPLICATION` icon only if that fails. Used by `tray.rs` (tray icon), `settings_dialog.rs`, and `progress.rs` (both dialogs' `WNDCLASSW.hIcon`, so the title bar/Alt-Tab icon isn't the Windows-default generic one) - one shared loader so all four UI surfaces (tray, Task Manager/Explorer, Settings window, progress dialog) show the same icon by construction, not by keeping four copies in sync by hand.
- `uifont.rs` - DPI-correct message font (`SystemParametersInfoForDpi`, cached per DPI) and 96-DPI design-unit scaling shared by `settings_dialog.rs`/`progress.rs`. Both dialogs are authored at 96 DPI; because the process is per-monitor DPI aware, the font and every control rectangle must be scaled together or labels overlap at 125%/150% scaling.
- `tray.rs` - tray icon + popup menu (Refresh now / Settings / Exit).
- `settings_dialog.rs` - modal Win32 dialog; state via `thread_local!` slots (safe because it's always modal). Interval parses with min 5, invalid input → 60. Has its own embedded progress bar (no status label) for its Refresh Now / OK-triggered refreshes, driven the same way as `progress.rs` (see below) via a local `WM_PROGRESS_UPDATE`. OK/Cancel are disabled (`EnableWindow`) for the duration of a Refresh Now, and - defense in depth, see "Concurrency" below - also explicitly no-op on `WM_COMMAND` if `REFRESHING` is somehow still true rather than trusting the disabled state alone.
- `progress.rs` - non-modal progress dialog shown only for manual refreshes (tray "Refresh now" / Settings OK). Starts with an indeterminate animated bar (cycling `PBM_SETPOS` on a timer) while the diary loads; switches to a real determinate bar the moment the first `WM_PROGRESS_UPDATE` arrives (wParam = tiles done, lParam = total tiles - posted per poster tile, from whichever worker thread finished it, by `wallgen::fetch_all_posters` via `wallpaper::refresh`'s `on_progress` callback) and updates the status label to `"Fetching posters (done/total)..."`. A `LAST_PROGRESS` high-water mark discards stale/out-of-order updates so the bar never visibly jumps backward. The refresh thread posts `WM_REFRESH_DONE` (wParam≠0 = failure, lParam = boxed error `String`) when done; failures keep the dialog open with the error + OK button. `progress::is_active()` guards against overlapping refreshes *from this one dialog's perspective only* - see "Concurrency" below for why that wasn't the whole story.
- `wallpaper.rs` - orchestrates a refresh: calls `wallgen::generate` (threading an `on_progress: &(dyn Fn(u32, u32) + Sync)` callback through), writes `wallpaper.jpg`, applies via `SystemParametersInfoW(SPI_SETDESKWALLPAPER)`; if lock screen is enabled, also calls `set_lockscreen_file` (see "Lock screen" below). `refresh()` and `apply_cached()` both take `RefreshGuard`, a process-wide mutual-exclusion lock - see "Concurrency" below; a second concurrent call gets a clear `Err` immediately rather than racing. `reqwest` blocking + rustls (no native-tls), with a `Wallboxd/<version>` User-Agent since it talks to Letterboxd and its poster CDN directly. Resilient by design: 60s timeout, up to 3 attempts with 5s backoff on `WallError::Network` (timeouts/connection/5xx across the RSS fetch or any poster fetch); `WallError::NotFound`/`Other` (bad username, no diary entries, bad image data) fail immediately - see `wallerror.rs`.
- `letterboxd.rs` - fetches `https://letterboxd.com/{username}/rss/` and parses it with `roxmltree` into poster URLs (`Vec<Option<String>>`, one per diary entry in feed order, `None` where an entry has no poster). Skips `/list/` items. Extracts the poster `<img src>` from each entry's HTML `<description>` via regex (mirrors the website's cheerio `$('p img')`), then normalizes it to the canonical 230x345 crop.
- `poster_layout.rs` - exact port of the website's `posterLayout.ts`: the edge-fill grid math (`compute_edge_fill_layout`, `rows_for_count`) and `sized_poster_url`, which snaps a poster URL's crop height up to Letterboxd CDN's fixed allowlist (`345, 450, 690, 750, 900, 1500, 1800, 3000` - anything else is rejected).
- `wallgen.rs` - the compositing itself, a port of the website's `wallpaper.jpg.ts`. **Poster fetching is concurrent, not sequential** - this was a real bug, not just a nice-to-have (see "Poster-fetch concurrency" below): `fetch_all_posters` runs `POSTER_FETCH_WORKERS` (8) worker threads over a shared `Mutex<VecDeque<usize>>` work queue inside `std::thread::scope`, each downloading+resizing (Lanczos3, via `image::imageops::resize`) one poster tile at a time and reporting completion through `on_progress` and an `mpsc::Sender`; results are collected back into an index-ordered `Vec<Option<RgbImage>>`. `generate()` then does the actual compositing single-threaded and fast (pure CPU, no network): allocates a white `RgbImage` canvas, overlays each fetched tile at its grid position, then fills the leftover edge margins by duplicating each row's edge-column poster (clipped to strip width) on both sides. Encodes to JPEG (quality 90) via `image::codecs::jpeg::JpegEncoder`. `MAX_TILES` (60) caps how many posters one wall composites, matching the old API's CPU/memory guard; `POSTER_FETCH_TIMEOUT` (20s, applied per-request, separate from the client's general 60s timeout) bounds how long one bad connection can occupy a worker.
- `wallerror.rs` - `WallError` (`NotFound` / `Network` / `Other`) classifies failures from `letterboxd.rs`/`wallgen.rs` by retryability for `wallpaper.rs`'s retry loop.
- `config.rs` - serde JSON config; `WallpaperStyle` maps to Windows registry values. `enabled` is the master switch (default `false`) - nothing runs automatically (startup/timer/post-settings-save refresh) unless it's on; manual actions (tray "Refresh now", Settings' own "Refresh Now") bypass it since clicking them is itself explicit consent. `username` defaults to `"abusayed"` as a working example, harmless since `enabled` defaults off.
- `autostart.rs` - dual-path on package identity (same `GetCurrentPackageFullName` check as the lock screen API in `wallpaper.rs`): unpackaged exe uses `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (exe path written quoted); the packaged MSIX build uses `Windows.ApplicationModel.StartupTask` instead, since registry Run keys and the Startup folder are both documented as unsupported for MSIX/Desktop Bridge apps (see `packaging/AppxManifest.xml`'s `desktop:StartupTask` extension, `TaskId="WallboxdStartupTask"` - must match `autostart.rs`'s `TASK_ID` exactly). `set()` always spawns a thread rather than running inline - confirmed by testing that `StartupTask::RequestEnableAsync` (hit whenever a task moves from Disabled back to Enabled, not just first-ever run) can block for 30s+ when called from the main thread before the message loop is pumping, with the whole process never reaching `create_main_window`.
- `applog.rs` - append-only timestamped log, one process-wide `Mutex` serializing writes. Needed: `writeln!` issues several small `write` calls per line, so concurrent callers (main thread, refresh threads, the autostart thread) could interleave mid-line even though each individual `WriteFile` with `FILE_APPEND_DATA` is itself atomic - confirmed by observing corrupted/merged log lines under concurrent writes before this fix. Formats each line into one `String` first, writes it in a single `write_all`.

## Gotchas

- **Wallpaper style registry values must be written BEFORE `SPI_SETDESKWALLPAPER`** - Windows reads them at apply time, not after.
- Offline story is intentional: `apply_cached()` re-applies the cached `wallpaper.jpg` (and `lockscreen.jpg`, if enabled) at startup; any refresh failure leaves the cache and current wallpaper untouched. No separate fallback path.
- `WallpaperStyle` registry encoding: Fill=10/0, Fit=6/0, Stretch=2/0, Center=0/0, Tile=0/1, Span=22/0.

## Poster-fetch concurrency - don't regress this to sequential

The first local-generation implementation fetched poster tiles one at a time in a plain loop. Measured against real Letterboxd data (`abusayed`, a 40-tile 4K wall): **72 seconds total**, with individual poster fetches ranging from 60ms to 9.2s - Letterboxd's CDN latency is just that variable per-request. Combined with a progress dialog that only ever showed a static "Refreshing wallpaper..." label and a fake bouncing bar, this read as a hang, not a slow operation - that's the "refresh is hanging" / "no proper update on the UI" bug. Fixed two ways, both load-bearing:

1. **Concurrency** (`wallgen::fetch_all_posters`, `POSTER_FETCH_WORKERS = 8`): the same 40-tile 4K wall composites in ~2s instead of 72s. If you touch this function, keep it concurrent - reverting to a sequential loop reintroduces the original bug even though it'd look like a harmless simplification in a diff.
2. **Real progress reporting**: `generate()`'s `on_progress` callback fires once per completed poster tile and is threaded all the way to both progress UIs. `progress.rs`'s floating dialog switches from an indeterminate animation to a real determinate bar and updates its status label to `"Fetching posters (done/total)..."`; `settings_dialog.rs`'s embedded bar (no label control there) switches to determinate the same way but stays textless. Don't let a future refactor silently drop `on_progress` back to a no-op outside of the intentional silent-timer-refresh path (`main.rs`'s `spawn_refresh`, which passes `&|_, _| {}` on purpose).

`POSTER_FETCH_TIMEOUT` (20s) is deliberately shorter than the client's general `REQUEST_TIMEOUT` (60s, `wallpaper.rs`) - posters are small static CDN images with no cold-start excuse for taking that long, and with 8 concurrent workers one stuck request otherwise ties up 1/8 of the pool for way too long.

## Concurrency: two refreshes could race on the same files - fixed with `RefreshGuard`

Found during a deliberate sanity-check pass (not reported by a user, but real and reachable): nothing stopped two `wallpaper::refresh()`/`apply_cached()` calls from running at once.

**How it was reachable**: the tray icon's "Refresh now" stays fully clickable while the Settings dialog is open. `EnableWindow(owner, false)` (called by `settings_dialog::show()` to disable the main hidden window while the dialog is up) does **not** block `WM_TRAYICON` - that's a custom app-defined message (`WM_APP + 1`) Shell32 posts directly to the window regardless of its enabled state, not a standard input message `EnableWindow` filters. So: open Settings, click its own "Refresh Now" (spawns a background thread, disables Settings' own OK/Cancel/Refresh buttons via `REFRESHING` - but nothing outside the dialog), then right-click the tray icon and pick "Refresh now" before the first one finishes. `progress::is_active()` (the tray path's guard) only tracks the *floating* progress dialog, has no idea Settings' own refresh is running, and lets a second `wallpaper::refresh()` start - two concurrent calls, no timing luck required.

**What that could actually break**: both calls write `wallpaper.jpg`/`lockscreen.jpg` at the same path concurrently, and both run `set_lockscreen_file`'s unique-file cleanup loop, which deletes every `lockscreen_*.jpg` **except its own call's file**. If call A's cleanup runs after call B has created its unique file but before B has finished using it, A deletes B's file out from under it - a plausible explanation for any future report of intermittent "failed to set lockscreen" errors with no obvious cause. `apply_cached()` does the identical file writes and is independently reachable (e.g. it runs synchronously on the UI thread immediately after saving Settings, which could overlap a tray-triggered refresh still running in the background), so it was exposed to the same race, not just `refresh()`.

**The fix**: `RefreshGuard` (`wallpaper.rs`) - a single process-wide `AtomicBool`, acquired via `swap` at the top of both `refresh()` and `apply_cached()`, released via `Drop` when the guard goes out of scope (so early returns via `?` can't leak it held). A second concurrent call gets `Err("Another refresh is already in progress...")` immediately instead of racing. `wallpaper::is_in_progress()` exposes a read-only check that `main.rs` (tray "Refresh now", the post-settings-save auto-refresh, and the timer) and `settings_dialog.rs` (its own Refresh Now button) all now check *before* spawning, so a busy click fails fast with no dialog flash - `RefreshGuard` itself remains the authoritative safety net regardless of whether that pre-check was accurate at click time. Also added, defense in depth: `settings_dialog.rs`'s OK/Cancel `WM_COMMAND` handlers now explicitly no-op if `REFRESHING` is true, matching the check `WM_CLOSE` already had - they were relying solely on the buttons being disabled, which is correct under normal interaction but wasn't defended against directly.

**Verified, not just reasoned about**: `wallpaper::tests::concurrent_refresh_guard_rejects_overlap` spawns 8 threads racing `RefreshGuard::try_acquire()` simultaneously and asserts exactly 1 wins and 7 are rejected - run 6 times during development, consistent every time. This is the one real test in the repo (see "Build / verify" above); it needs no network and runs in ~0.2s, so there's no excuse for `cargo test` to skip it going forward.

If you touch this again: don't remove `RefreshGuard` from either `refresh()` or `apply_cached()` to "simplify," and don't add a new refresh-triggering code path (a new button, a new timer, a Store-specific auto-update hook, whatever) without going through one of them - that guard is the only thing preventing the file race described above.

## Lock screen - resolved; here's the full investigation so it isn't repeated

`set_lockscreen_file` (`wallpaper.rs`) sets the lock screen image. This took multiple rounds of live testing to get right, and the trail matters if it ever breaks again - every hypothesis below except the last was implemented, tested on a real machine, and disproven, in this order:

1. **Discarded success/failure signal (real bug, fixed first).** The original code called `UserProfilePersonalizationSettings.TrySetLockScreenImageAsync`, a WinRT API that **does not throw on failure** - it resolves to a `bool` (`true` iff Windows actually applied the image), and the original code discarded that bool entirely. A declined request looked byte-for-byte identical to success: `refresh()` logged "wallpaper refreshed", no error ever appeared, and the lock screen just silently never changed. Reported as "the wallpaper is working but the lockscreen is not being setup." Fix: capture and check the bool.
2. **Lock screen mode (Picture vs. Spotlight/Slideshow/third-party) - tested, disproven as sufficient.** Docs suggest `TrySetLockScreenImageAsync` needs plain "Picture" mode. On this machine the lock screen was initially managed by a third-party Store app (`55888ChristopheLavalle.DynamicTheme`) registered as the active background provider. Even after fully uninstalling it (not just toggling its own settings) and hand-picking a fresh picture via Windows Settings (confirmed via the registry's `ImageId_C`/`Details_C = "IMMERSIVE_CPL"` marker - the standard signature of "set through Windows' own Settings picture picker"), `TrySetLockScreenImageAsync` still returned `Ok(false)`.
3. **Package (MSIX/APPX) identity - confirmed necessary, but not sufficient alone.** A plain unpackaged `.exe` has no package identity; `GetCurrentPackageFullName` (`windows::Win32::Storage::Packaging::Appx`, feature `Win32_Storage_Packaging_Appx`) returns `APPMODEL_ERROR_NO_PACKAGE` (15700) - confirmed identical for a plain `powershell.exe` too, i.e. the standard state of any unpackaged Win32 process. `set_lockscreen_file` checks this up front and fails fast with an accurate message. Packaging as MSIX (`packaging/`, Desktop Bridge: `EntryPoint="Windows.FullTrustApplication"` + `rescap:runFullTrust`) fixes this specific failure - confirmed live, `GetCurrentPackageFullName` succeeds when launched through the package. **But `TrySetLockScreenImageAsync` still returned `Ok(false)` even with identity present**, mode re-confirmed as genuine Picture, and no competing provider installed.
4. **`PackageSignatureKind` (Developer vs. Store) - investigated, inconclusive, not the actual fix.** The sideloaded/self-signed test package reported `SignatureKind = Developer` (1), not `Store` (3) (`windows::ApplicationModel::Package::Current()?.SignatureKind()`). Plausible remaining suspect at the time, but never confirmed - no Store-signed build existed to compare against (the public Store listing returned `ProductNotFound` throughout this investigation).
5. **Same-filename caching - tested, disproven.** Theory: the API might decline a new image with the exact same filename as the previously-set one (the app always applied from `lockscreen.jpg`/`wallpaper.jpg`, filename never changing). Worked around by copying to a uniquely-named file (`lockscreen_{timestamp}.jpg`, old ones cleaned up after) before each attempt. **Tested directly and it did not fix the decline**: confirmed a genuinely new file was created and used, `TrySetLockScreenImageAsync` still returned `Ok(false)`.
6. **The actual fix: use the older `LockScreen.SetImageFileAsync` API instead.** `windows::System::UserProfile::LockScreen::SetImageFileAsync` (not `UserProfilePersonalizationSettings`) - an older, pre-`UserProfilePersonalizationSettings` UWP API that throws a real exception on failure instead of silently returning `false`. **Confirmed working end-to-end**: built the MSIX with this change, installed, launched through the package, and - rather than trusting "no exception was thrown" alone - read back `LockScreen::OriginalImageFile()` immediately after calling it, which reported exactly the freshly-set file path (`file:///.../lockscreen_<timestamp>.jpg`), confirmed across two independent fresh launches. This is the API's own authoritative record of the current lock screen image, not an inference - the fix genuinely works.

Kept the unique-filename copy (step 5) alongside the new API (step 6) even though it wasn't re-tested for necessity with `LockScreen.SetImageFileAsync` specifically - it's harmless (a plain file copy with real cleanup logic, no behavior change on the success path), and there was no reason to remove working, low-risk code just because it solved a different API's problem.

**If you touch `set_lockscreen_file` again:**
- Don't switch back to `UserProfilePersonalizationSettings.TrySetLockScreenImageAsync` - it was tested extensively (steps 1-4 above) and never worked from this app, packaged or not.
- Don't re-chase "lock screen mode" or "same filename" as explanations if something regresses - both were implemented and directly disproven.
- If it ever silently stops working again, verify with `LockScreen::OriginalImageFile()` read back immediately after the call, the same way this was actually confirmed - don't trust "no exception" alone as proof, and don't trust registry archaeology (`HKCU\...\Lock Screen`'s `ImageId_A/B/C/D` rotation-cache structure never reflected this API's changes in testing, even when the change was independently confirmed working via `OriginalImageFile()`).

## Icon: `assets/icon.ico`, tray + exe identity from one file

`assets/icon.ico` is a proper multi-resolution icon (16/32/48/256px frames, PNG-compressed per frame - the modern Vista+ ICO format), navy `#1B2A41` rounded-square background with a gold `#E8B84B` "W" mark, same palette as `packaging/Assets/*.png` and `assets/logo.png` (the README header image), built via a PowerShell/`System.Drawing` script plus a small hand-written Python ICO-container assembler (`System.Drawing.Icon` can't itself export a multi-frame PNG-compressed ICO - only single-frame). **This is the production artwork** - `assets/icon.ico`, `assets/logo.png`, and `packaging/Assets/*.png` are final, not placeholders to swap out before Store submission.

`build.rs` embeds it into the exe at resource ID `"1"` (`winresource` build-dependency); `tray.rs`'s `app_icon()` loads that same resource ID for the tray icon. One file, one embed step, both surfaces (tray + Explorer/Task Manager/Alt-Tab, which read the exe's lowest-numbered icon resource automatically) show the same icon by construction.

**Verification gotcha**: `[System.Drawing.Icon]` constructed directly from the `.ico` file path (`New-Object System.Drawing.Icon(...)`) fails to render PNG-compressed frames correctly in this environment - `.ToBitmap()` produces visual garbage despite the file being byte-perfect (independently verified: every frame's declared offset in the `ICONDIRENTRY` table points to a valid PNG signature, sizes and total file length all check out exactly). This is a known legacy `System.Drawing.Icon` limitation with PNG-in-ICO, not a real problem - confirmed by the actually-meaningful check instead: `[System.Drawing.Icon]::ExtractAssociatedIcon("...\Wallboxd.exe")` (which uses shell icon extraction, the same code path Explorer/Task Manager use) correctly returns the branded icon. If you need to re-verify the icon after a change, use `ExtractAssociatedIcon` on the built exe, not a direct `Icon` constructor on the loose `.ico` file - the latter will falsely look broken.

Live desktop screenshots (tray icon specifically, taskbar area) could not be captured in this environment to visually confirm - `CopyFromScreen`, even targeting the taskbar's exact on-screen rectangle as reported by `GetWindowRect` on the real, visible `Shell_TrayWnd` window handle, only ever captured the desktop wallpaper, never real taskbar/tray composition. Whatever session this automation runs in doesn't have access to the interactive desktop's actual composited output. This is an environment limitation, not evidence of anything wrong with the icon - treat the `ExtractAssociatedIcon` check above as the real verification, and if a screenshot-based check is ever attempted again here, don't waste time on it past the first "wallpaper instead of taskbar" result.

## Letterboxd CDN rules - undocumented by Letterboxd, confirmed by testing

Wallboxd talks to Letterboxd directly - see "Architecture" above. The rules below aren't documented anywhere by Letterboxd; kept here as reference since they're exactly what `poster_layout.rs`/`letterboxd.rs` implement.

- Diary RSS: `GET https://letterboxd.com/{username}/rss/` - up to 200 `<item>`s, most recent first; `404` if the username doesn't exist. Each entry's poster URL lives inside the HTML in `<description>`, as the first `<img src>` under a `<p>`.
- Poster CDN (`a.ltrbxd.com`) sizing - **critical gotcha**: it only honors an **exact 2:3 ratio** AND a **hard allowlist of crop heights**: `345, 450, 690, 750, 900, 1500, 1800, 3000`. Anything else is rejected outright. `poster_layout::sized_poster_url` snaps a requested height up to the smallest allowlisted value ≥ it (`h=800` → `900`); below 345 / above 3000 clamps to the nearest end. Request the actual pixel height you'll resize down to - more wastes bandwidth, less upscales and looks soft.
